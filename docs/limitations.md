# What LogicScout shows today and what it does not

This page answers, point by point, the questions a careful reviewer should ask about LogicScout, and it is written so that each answer can be checked against the code and against the raw benchmark files rather than taken on trust. Where we changed something in response, a short note after each answer says what is now measured and where the number lives, and where we have not, the answer says so. Numbers come only from measurements on the current code and from [results.md](results.md), and a measurement that had not finished when this page was written is described rather than given a value.

The short version is that LogicScout is a working research prototype which learns executable rules for compact simulated systems through chosen experiments, compiles a controller from them and watches for those rules to stop holding, and that the evidence so far supports that narrower description far better than it supports any claim of general autonomous system discovery.

## The model's contribution has not been demonstrated

On the relay world the variant that runs with no model at all, using only rule induction in code, the planner and the drift monitor, matched the full pipeline on held-out goal success (0.50 and 0.25 against 0.50 and 0.25) and was slightly better on prediction accuracy, while the full pipeline spent about 140,000 tokens per run to get there. That means the goal successes we reported on relay come from the code-side rule fitting and planning rather than from the model, and nothing we published before this page shows that adding Nemotron improves control on any world. The two runs were also not perfectly paired, because the no-model row came from a separate driver with different lab seeds, even though the referee cases were the same.

**What is measured now.** The bench now has arms that never call the model (`no_model`, `tabular`, `random` and `idle`) and arms that do (`full` and `model_only`), all run by one command over the same lab seeds and the same held-out referee cases, so that the earlier separate driver is no longer needed. At the time of writing only the arms without model calls had finished, so the model's marginal effect on goal success is still not established, and until the model arms finish on the same systems we make no claim that Nemotron improves control.

## The sample was far too small to support a ranking

The first benchmark used two seeds and four held-out cases per seed, so the headline 0.50 and 0.25 are two successes out of four and one out of four, three successes in eight cases overall. A zero for a baseline over four cases does not mean its true success rate is zero, and none of these numbers can rank one arm above another with any confidence.

**What is measured now.** Every arm now reports its successes and its case count next to a Wilson 95% interval. On relay with objective `bulk8`, eight seeds with four held-out cases each, the arm without the model reached the goal in 4 of 32 cases (0.12, interval 0.05 to 0.28), while the tabular baseline, random and idle control reached it in none of 32 (interval 0 to 0.11). On 20 generated Forge systems with six held-out cases each, the arm without the model succeeded in 22 of 120 cases (0.18, interval 0.12 to 0.26), the tabular baseline in 0 of 120 (interval 0 to 0.03), random control in 2 of 120 (interval 0 to 0.06) and idle control in none. The intervals overlap on relay, so the larger sample shows that learning rules beats the simple baselines on Forge but not yet on relay, and the relay success rate at this scale is lower than the 0.50 and 0.25 of the first two seeds suggested.

## Prediction accuracy can hide the transitions that matter

The headline prediction score counts, field by field, how many readings the theory predicted correctly on a single step, so a counter that never moves counts as much as the reading the goal depends on, and a theory that predicts "nothing changes" on a mostly quiet system already scores well, which is why the persistence baseline sat at 0.76. The score was also collected under a random action policy rather than under the controller's own behaviour, and numeric readings were compared with a single global tolerance of 2% relative error, which on a large reading can let a wrong prediction count as correct.

**What is measured now.** The referee now also reports accuracy restricted to the readings whose value actually changed on a step, where "nothing changes" scores 0.0 by construction, open-loop rollout accuracy where the theory predicts up to five steps ahead from its own predictions without being corrected by observations, and accuracy on the readings the goal depends on, and it pools transitions collected under the controller's own behaviour with those from the random policy. When the theory learned in the recorded relay run was scored again this way on eight held-out cases, its plain per-field accuracy stayed at 0.87 against 0.76 for persistence, but on the 446 readings that changed it was right only 0.60 of the time, its accuracy fell from 0.86 one step ahead to 0.62 five steps ahead, and on the goal readings (`delivered` and `lost`) it was 0.70. Those lower figures are the honest picture of how well the theory understands the consequential part of relay. The same measures for theories learned without the model on each world, five seeds each, show how uneven the picture is, since accuracy on changed readings was 0.58 on relay, 0.36 on plant, 0.38 on rover, 0.14 on orbit, 0.46 on gate and 0.90 on Forge, against plain per-field accuracy between 0.78 and 0.95 on the same worlds. The global 2% numeric tolerance is unchanged.

## The controller was validated against the model that produced it

A compiled playbook was accepted when it reached the goal in a simulation run on the learned theory from a single starting observation, and the planner fallback searches that same theory, so a theory that is wrong in a convenient way could approve a controller that fails on the real system. In addition, when neither the model-written playbook nor the planner reached the goal in simulation, the closer of the two was kept and still logged as compiled, which made a compiled playbook look more trustworthy than it was.

**What is measured now.** Before a controller is put in charge it now runs a reality trial on the actual system, on a separate sandbox session reset to a lab seed other than the one it will operate on and using only the scout's own port, so that the theory's simulated outcome can be compared with what really happened and every one-step prediction can be checked against the real observation. Success in the trial is judged by the objective's own success expression on real observations rather than by privileged ground truth, and a controller is rejected when the goal it reached in simulation is not reached in reality or when more than half of the real steps contradict the theory. A rejected trial adds its transitions to the scout's experience, the theory is refitted without model calls and the controller is compiled again, with at most two trials per compilation, and every trial step is charged to the probe budget and logged as a `playbook.trial` event. After a hidden change the trial session replays the changes applied so far, so later trials test the current system. Trial outcomes are counted per run in the run metrics, and we have not yet aggregated how often trials reject controllers across many runs, so the trial is a guard against model exploitation whose effect on held-out success is still to be measured. Separately, the controller is checked against rival theories that also fit the experience, as described under uncertainty below.

## The baselines were not matched on budget or horizon

The full pipeline used 100 probes, 50 before and 50 after the hidden change, whereas random probing used 50 and the no-adaptation arm used 62, so the end-to-end comparisons mixed the effect of a method with the effect of more experiments. The per-step model arms were run on three cases with a 12-step cap instead of the 40-step horizon, and on that same capped subset the compiled playbook also scored zero, which means the comparison we highlighted between a compiled controller and per-step model control does not show an advantage at all. The comparison between the full pipeline and the no-adaptation arm also changed the drift monitor, the extra probes and the theory rebuild together, so it cannot isolate the value of detecting the change.

**What is measured now.** The new bench runs every arm on the same systems, the same held-out cases and the same horizon, and the arms without the model share one probe budget. The tabular arm is a simple classical learner that records what each action did in each observed situation, which is a first step towards the stronger classical baselines discussed below. Arms that cannot be matched are kept out of the main comparison.

## The generated worlds are close to what the learner already expects

Forge composes each system from eight mechanism families with narrow parameter ranges, namely delay, cooldown, window, capacity, resource, ordering, control and threshold, and the code-side miner searches exactly the delays, cooldowns and periods that the generator produces. A new Forge seed is therefore a new combination of familiar parts rather than a system containing an unfamiliar mechanism, and the test in which a theory written from the true rules predicts every generated system perfectly shows only that the rule language can express those systems, not that the scout can discover them from limited observations. Forge goals are calibrated with a beam search over four starting seeds, which makes them reachable in practice but is not a proof of reachability for every evaluation case.

**What is measured now.** Forge can now also build out-of-family systems (`x<seed>`) whose mechanisms lie outside the eight families and outside what the miner searches for, namely measurement noise, saturation, a hidden three-mode state and slow drift, and it reports how well the best theory the DSL can express predicts each of them. Running the scout without the model on 10 ordinary Forge systems and 10 out-of-family systems, six held-out cases each, it reached the goal in 13 of 60 cases (0.22) in family and in only 6 of 60 (0.10) out of family, where random control reached 9 of 60 (0.15), so outside the familiar families the scout did worse than random play. Its prediction accuracy fell from 0.92 to 0.72, and from 0.88 to 0.57 on changed readings, and most of that loss is shared by the best theory the rule language can express (1.00 against 0.78), because the language cannot represent noise, saturation, hidden modes or wear and the scout does not invent them. The full table is in [forge.md](forge.md), and with ten systems per arm a difference of a few cases is within noise. This result is the clearest statement of the limit on generality, since LogicScout has been evaluated on compact simulated systems and it does not yet discover mechanisms its rule language cannot express.

## Learned rules are behaviourally equivalent, not necessarily the true laws

Two different mechanisms can produce identical observations for every experiment a limited budget allows, for example a six-step cooldown and an internal counter that happens to cycle every six steps, and no learner can tell them apart without an experiment that separates them. What LogicScout learns is therefore a set of rules that are behaviourally equivalent to the hidden laws within the range it tested, and those rules can diverge from the real system under interventions it never tried. The debrief shows the true laws next to the learned ones so that a reader can see where the two agree by mechanism and where they only agree by outcome.

## Experiment selection is a disagreement heuristic

The investigator scores a candidate probe by counting how many predicted readings differ between rival hypotheses at each simulated step, averaged over the length of the probe. That is a useful heuristic, but it does not weigh hypotheses by their probability, does not estimate information gain, ignores the cost or risk of a probe, treats all readings as equally important, and cannot find a mechanism that every current hypothesis misses in the same way, so describing it as choosing the most informative experiment would overstate it. The code-side miner and the residual checks on mismatches are what give the scout a route to explanations outside the current hypothesis set, and they have not been evaluated separately.

## The systems are deterministic, discrete and small

Every world LogicScout has been evaluated on is a compact simulation with integer or boolean readings and deterministic laws, plus one HTTP service written for the project, so we have no evidence about stochastic dynamics, noisy sensors, continuous physics, partial observability beyond a few hidden variables, or wear. A finite set of deterministic rules may be a poor representation of such systems, and the industrial domains named in the world titles describe the flavour of each simulation, not a claim that LogicScout can operate those systems in practice.

## Uncertainty was not carried into control

During investigation the scout keeps rival hypotheses, but the controller used to be compiled from a single best theory, so a choice the evidence could not settle was resolved silently rather than planned around.

**What is measured now.** Rival theories whose rules fit the experience equally well are now kept after investigation, and when a revision finds a supported rival as accurate as the rule it would replace, the theory records the two as equivalent so far rather than silently picking one. When more than one plausible theory remains, control switches to a robust planner that chooses the action whose worst outcome across those theories is best, breaks ties by how little the theories disagree about the readings the goal depends on and only then by the average outcome, and records that disagreement at every step. The planner used when a single theory remains is unchanged. This is covered by tests on constructed cases, and its effect on held-out goal success has not yet been measured across runs, so we do not claim that robust control improves success.

## Drift detection and recovery are inconsistent

The hidden change was detected and recovered from on one of the two full-pipeline seeds, detected 11 steps after the change in that seed and not detected at all in the other, while the no-model runs detected it after 4 and 45 steps and recovered in only one. The live recording shows a run that detected the change and did not complete recovery. The monitor itself has known weaknesses, since it infers sensor resolution from the smallest gap between readings it has happened to observe, which can hide a real error when observations are sparse, it updates its notion of normal behaviour while a change is only suspected, which can absorb a gradual change, and it permanently discounts rules that were implicated once and not repaired. We have not measured false-alarm rates, the distribution of detection delays, gradual drift or several changes in sequence.

**What is measured now.** Detection, false alarms and recovery are now reported per run, with detection delays listed individually so that failures stay visible rather than being averaged away. In the runs without the model, with the change applied after 40 control steps, relay detected the change in 7 of 8 runs with a median delay of 8 steps but two delays of 131 and 162 steps, recovered in only 2 of 8, and raised a false alarm before the change in 2 of 8 runs. On 20 Forge systems the change was detected in only 3 runs and recovered from in 2, with false alarms before the change in 5. Detection and recovery therefore remain the weakest part of LogicScout, and the monitor weaknesses listed above have not been fixed.

## The rule language prevents code execution, not unsafe actions

The DSL accepts only a whitelisted syntax tree with no imports and no attribute calls, which keeps generated rules from executing arbitrary Python, but a perfectly sandboxed rule or playbook can still command an actuator past its limit, cycle a valve repeatedly or drive the system into a dangerous state. Argument ranges were only checked for literal values, so an argument computed from a reading could fall outside its allowed range at run time. Experiments are also unconstrained, and the most informative probe can be the most dangerous one.

**What is measured now.** A world's manual can now declare safety limits as DSL conditions on the readings, such as the plant's alarm limits, which are published to the operator and are not the hidden laws. Every real observation is checked against them and every breach is logged and counted, and before acting, the control policy and the probes are filtered by predicting the next reading with the learned theory, so an action the theory expects to break a limit is not taken and an experiment is cut short before such a step. Prevention is therefore only as good as the theory, a breach the theory cannot foresee still happens, which is why breaches are counted rather than assumed away, and a limit nobody wrote down is not enforced. The number of breaches across runs is not yet reported.

## The logbook digest shows integrity of a local chain, not tamper-proofing

Every logbook event carries a sha256 digest over its sequence number, run id, kind, data and the previous digest, and `Logbook.verify` recomputes the chain. That detects an edit to a single stored event, but the timestamp and phase are still outside the digest, and a party that controls the whole log can rewrite it and recompute every digest, so on its own the chain only shows the integrity of a local digest chain.

**What changed.** When a run finishes, the head of its chain, meaning the final digest, the event count and the time, is now recorded in `data/anchors.jsonl`, which is kept in the repository so that git history and the public remote act as an external record. A log rewritten after its head was published no longer matches its anchor, which `logicscout verify` checks. The anchor proves integrity since anchoring, not that what the log says is correct, and it says nothing about a run that was never anchored or whose anchor was never published.

## Isolation and leakage checks are static audits

The scout, model and briefing packages are checked by an AST scan for imports of the worlds or the referee and for reads of law attributes, and the prompt log is searched for law sentences and law values. Those checks catch the obvious ways hidden laws could reach the model, but they are a static audit and a string search rather than a process boundary or an information-flow proof, so a paraphrased law in a prompt would not necessarily be caught. Hidden changes and ground-truth success are applied by the mission orchestration through the sandbox's admin interface, which the model never sees, and running the scout in a separate process that holds only the scout token would make that separation enforceable rather than conventional.

## Internal validation reused the data it learned from

The investigator accepts a revision when accuracy on all accumulated transitions does not fall, so revisions are selected against the same experience that suggested them, and the code-side miner's held-out split assigns individual transitions rather than whole episodes, so neighbouring steps of one trajectory can land on both sides of it. The referee's held-out cases remain untouched by either process, which is why the referee's numbers rather than the investigator's are the ones we report, but the internal acceptance step can overfit and should split by episode.

## Reproducibility of the first benchmark

The first relay benchmark ran on a commit plus uncommitted changes, and the no-model row came from a short driver that was not published with it, so that tree cannot be reconstructed exactly. The new runs are produced by the bench command alone, whose invocations are listed in `logicscout/bench/__main__.py`, with the raw output of every run under `data/bench/`.

## Known defects in the application

The what-if endpoint and the manual and controller exports look up the manual and reopen the session by world id without the Forge variant, so for a generated system they can validate against and test on the standard Forge system instead of the one the scout learned, and the exported `controller.py` does not pass the variant either. The HTTP API has no authentication or per-run ownership, so on a shared deployment anyone can list runs, read their events, stop a run or inject a hidden change, which is acceptable for a public demonstration and not for a multi-user service. Live event streams use unbounded per-subscriber queues. The exported controller runs without the model, but it still needs a compatible interface and has no handling for lost connections, unavailable readings or restarts, so what it demonstrates is execution without the model rather than independent deployment.

## Public sources are an untested trust boundary

Tavily results are turned into prior hypotheses that experiments must confirm or overturn, which protects against wrong facts but not against a page written to steer the model, and we have not tested the briefing against prompt injection. The DSL limits what a manipulated rule can execute, but not which hypotheses, probes or controllers a manipulated prompt might favour.

## Classical baselines and cost

LogicScout has not been compared with established system-identification methods, finite-state model inference, Bayesian experimental design or model-based reinforcement learning, and the code-only arm is the closest thing to a classical baseline in the results. The cost that matters is the total cost per successfully controlled system, including model tokens, probes and recovery, and on relay the model added tokens without adding successes.

**What is measured now.** The bench records tokens and probes for every arm, so cost per held-out success can be read directly once the model arms finish. The tabular arm is the first classical comparator, and it reached the goal in none of the 152 relay and Forge cases above.
